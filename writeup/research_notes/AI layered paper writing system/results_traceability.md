# Results-to-text traceability and automated consistency checking

Scope: tools and practices that tie each number or claim in a paper's text to the code and data behind it, and that check text against results automatically. Written for an AI-written JoFE LaTeX paper whose numbers are already macros generated by Python scripts. Missing numbers already print a visible "pending" marker, and the build already fails on undefined references. Research date: 2026-10-28. Note on method: the data-to-paper and Gentzkow-Shapiro PDFs were downloaded and read in full text with pdftotext. Everything else comes from abstracts, documentation pages, or search summaries, and is flagged where it was not checked against the primary text.

Local context checked: the repo's macro files (e.g. `writeup/generated/rehaul_oos_numbers.tex`) open with an `AUTO-GENERATED by writeup/make_rehaul_oos_table.py -- do not edit` header. Each `\newcommand` carries a trailing `%` comment that describes the value. A hand-maintained markdown claims ledger also exists (`writeup/CLAIMS_LEDGER_2026-08-06.md`), with claim / number / section columns and tiers. The recommendations below build on these.

## Q1. data-to-paper (Kishony lab, Technion): how does backward traceability work, and what did its evaluation find?

### Takeaway
data-to-paper gives every numeric value in the code outputs and tables a label (a LaTeX hypertarget). The writing LLM must wrap every number it writes in a hyperlink to one of those labels, or use `\num(<formula>, "explanation")` for a derived value. A rule-based check rejects any number that is not hyperlinked or whose link target does not match. A placeholder such as `[unknown]` aborts the whole run. Each cited number therefore chains back through a "Notes" appendix, then the table, then the output file, then the exact code lines. Even so, fully autonomous runs had fundamental errors in about 10-20% of papers on simple goals and failed consistently on complex ones. Most of these errors were interpretation and analysis errors, not mistyped numbers.

### Cited Findings
**Publication and dates**
- The paper is "Autonomous LLM-driven research from data to human-verifiable research papers" by Ifargan, Hafner, Kern, Alcalay and Kishony. arXiv:2404.17605 v1 was submitted 24 Apr 2024 — [arXiv](https://arxiv.org/abs/2404.17605).
- It was published in NEJM AI (DOI 10.1056/AIoa2400555), cited as 2025 vol. 2 no. 1. A search summary says the PDF gives 3 Dec 2024 as the publication date (not independently verified) — [Kishony lab PDF](https://kishony.technion.ac.il/wp-content/uploads/2024/05/AIoa2400555.pdf); [GitHub](https://github.com/Technion-Kishony-lab/data-to-paper).
- The code is open source (MIT) — [GitHub](https://github.com/Technion-Kishony-lab/data-to-paper).

**Architecture**
- Multiple LLM agents and rule-based agents are guided through pre-defined "research steps". Each step's product is extracted from the LLM response and goes through rule-based review first, then LLM review, then optional human review. A failed rule becomes a feedback message to the LLM — [arXiv PDF](https://arxiv.org/pdf/2404.17605).
- Each step sees only the prior products it needs. The authors say this "minimizes possible hallucinations due to mixing relevant and irrelevant information" and lets the system "trace, verify and chain the sources of numeric results cited by the LLM" — [arXiv PDF](https://arxiv.org/pdf/2404.17605).

**Information tracing (verbatim mechanism, Methods)**
- The system tracks "the specific code lines producing each file output, the translation of these outputs into tables and the incorporation of numbers from the table in the Results section."
- It "programmatically assign[s] a unique label for each numeric value appearing in the prior products for the Results writing step." These values are shown to the LLM formatted "as LaTex hypertargets with their corresponding labels."
- The LLM is told to "wrap each numeric value that it writes with a LaTex hyperlink matching the corresponding label" — [arXiv PDF](https://arxiv.org/pdf/2404.17605).
- Derived numbers (unit changes, coefficients converted to odds ratios, etc.) use the syntax `\num(<formula>, "explanation")`. When the paper is compiled, "the \num commands are replaced with their value and a 'Notes' appendix is added listing all formulas with their explanation" — [arXiv PDF](https://arxiv.org/pdf/2404.17605).
- A rule-based check verifies "that, either as stand-alone or within a \num formula, each numeric value mentioned in the section is hyperlinked, and that the target of each link correctly matches the corresponding label provided in the prior product context" — [arXiv PDF](https://arxiv.org/pdf/2404.17605).
- Anti-hallucination fail-safe: the Results prompt tells the LLM to write the placeholder `[unknown]` for a missing value. If that or any other placeholder appears in the response, "data-to-paper abort[s] the entire research cycle" — [arXiv PDF](https://arxiv.org/pdf/2404.17605).
- The resulting chain: a Results number links to the "Notes" appendix (formula and explanation), then to the table cell, then to the output file the table came from, then "to the specific code lines which generated this output file". The paper presents this as clickable hyperlinks in its "Data-chained Manuscripts A-D" — [arXiv PDF](https://arxiv.org/pdf/2404.17605).
- The README: "any numeric values can be click-traced all the way up to the specific code lines that created them." Manuscripts are watermarked "Created by data-to-paper (AI)" — [GitHub](https://github.com/Technion-Kishony-lab/data-to-paper); [arXiv PDF](https://arxiv.org/pdf/2404.17605).

**Code guardrails** — code is checked at four levels [arXiv PDF](https://arxiv.org/pdf/2404.17605):
1. static checks of the required structure;
2. runtime checks (errors, warnings, restriction violations);
3. "package-specific guardrails": the allowed statistics packages are wrapped to catch common ChatGPT mistakes and to allow "rule-based review of p-value formatting";
4. output checks that the requested files exist, with the requested content and format ("Numerical data checks").

**Evaluation**
- The authors manually checked each manuscript and its run record for five things [arXiv PDF](https://arxiv.org/pdf/2404.17605):
  1. correct analysis;
  2. "that every statement in the text involving numeric information corresponds to the correct numeric value from the output of the data analysis";
  3. that each citation fits its context;
  4. overall exactness;
  5. quality of the writing.
  Highlights were green (correct), yellow (imperfect), orange (minor error) and red (major error).
- Open-goal runs (2 datasets × 5 papers): 2 of 10 papers had major, result-affecting mistakes. One misread a correct analysis after hallucinations in the goal step. The other ran an erroneous analysis that led to unfounded association claims — [arXiv PDF](https://arxiv.org/pdf/2404.17605).
- Fixed goals that reproduce published studies:
  - Challenge 1 (Saint-Fleur et al.): all 10 runs reproduced the analysis correctly, and 8 of 10 reached the correct overall conclusions. 2 of 10 had interpretation errors despite a correct analysis.
  - Challenge 2 (Shim et al., several ML models): the error rate was 90% with the original broad goal, against 10-20% with a narrower goal (fewer models) — [arXiv PDF](https://arxiv.org/pdf/2404.17605).
- Headline: "for simple research goals it can autonomously create reliable manuscripts in 80-90% of the cases." Adding 2-3 one-sentence human review comments per run, "typically in the code writing step," gave accurate papers even for the complex goals — [arXiv PDF](https://arxiv.org/pdf/2404.17605).
- An early-warning signal: the number of iterations needed to finish the Data Analysis step grows with task breadth, "providing a potential possibility to alert of too complex analysis" — [arXiv PDF](https://arxiv.org/pdf/2404.17605).
- Stated limitations [arXiv PDF](https://arxiv.org/pdf/2404.17605):
  - textual and table outputs only (no figures);
  - no follow-up questions;
  - hypothesis-testing research only;
  - "relatively limited" novelty;
  - the README says the process is "NOT error-proof and human intervention is necessary" ([GitHub](https://github.com/Technion-Kishony-lab/data-to-paper)).

### Inferences
- data-to-paper's reported major errors were wrong analyses and wrong interpretations, not numbers that failed to match outputs. This suggests hyperlinking plus the link check solves the transcription problem, and the remaining risk sits in the claims and conclusions (Q3). The paper does not give a separate count of number-mismatch errors, so this is an inference.
- The user's pipeline already has the equivalent of the "labelled value" layer (macros generated from results). What it may lack is data-to-paper's other three pieces:
  1. a lint that rejects any literal digit in prose that is not a macro;
  2. a formula-with-explanation route for derived numbers, compiled into a Notes appendix;
  3. a hyperlink chain to the table and script that a reviewer can click.

### Gaps
- Table S7 of the supplement (the full list of rule-based checks and placeholders) and Table S8 (the package guardrails) were not retrieved.
- Gao & Harrison's NEJM AI companion editorial (reported in a search summary as saying significant errors occur with complex datasets) was not read.
- No published follow-up evaluation of data-to-paper by third parties was found.

## Q2. Pipeline tools (showyourwork!, knitr/Quarto inline results, Gentzkow-Shapiro, Snakemake/Make, Manubot, MyST glue): how do they keep a stale number out of the PDF?

### Takeaway
There are three guarantee styles:
1. **Regenerate everything from scratch.** Gentzkow-Shapiro: one script runs the project, and you prove replicability by deleting all outputs and rebuilding.
2. **Dependency graph.** showyourwork! on Snakemake: `\variable{file}` registers the number file as a dependency of the PDF, and the PDF is rebuilt when the generating script or rule changes.
3. **Compute at render time.** Quarto, knitr and MyST inline expressions.

The compute-at-render tools all have documented staleness escape hatches (freeze, cache). None of these tools checks the claim a number supports. They only make sure the number is current.

### Cited Findings
**Gentzkow & Shapiro, "Code and Data for the Social Sciences: A Practitioner's Guide"** (dated 10 Mar 2014; the cover asks you to cite it as a "University of Chicago mimeo … last updated January 2014") — [PDF](https://web.stanford.edu/~gentzkow/research/CodeAndData.pdf)
- Automation rules: "(A) Automate everything that can be automated. (B) Write a single script that executes all code from beginning to end."
- Version-control rules: "(A) Store code and data under version control. (B) Run the whole directory before checking it back in."
- Directory rules: "(A) Separate directories by function. (B) Separate files into inputs and outputs. (C) Make directories portable."
- Motivation: without automation "there is no authoritative definition of what the numbers in our paper actually are."
- Worked example: tables move from a hand-assembled `tables.txt` to a code-produced `tables.tex` (Stata `outreg`). A `rundirectory.bat` ends in `pdflatex`. "Unlike a readme file … rundirectory.bat cannot be incomplete, ambiguous, or out of date." Test: "we can now delete all of the output files in the directory … and reproduce them by running rundirectory.bat."
- Correction to the brief: the 2014 guide itself, read in full text, does not describe writing in-text numbers to LaTeX macro files. That practice is widespread in economics workflows, but this guide does not source it (see Gaps).

**showyourwork!** (Luger, Bedell, Foreman-Mackey, Crossfield, Zhao, Hogg et al.; first used for arXiv:2110.06271, Oct 2021) — [arXiv listing](https://arxiv.org/abs/2110.06271); [GitHub](https://github.com/showyourwork/showyourwork); [LaTeX docs](https://show-your.work/en/latest/latex/)
- arXiv:2110.06271 is a science paper "Prepared using the showyourwork" workflow, not a methods paper about the tool.
- The repo describes it as "a workflow management tool for open source scientific articles" that "automates your entire workflow, packaging it into a self-contained recipe". At capture it had 666 stars, 63 forks and 1,948 commits (counts change over time) — [GitHub](https://github.com/showyourwork/showyourwork).
- `\variable{output/answer.txt}` is an alias of `\input`. The difference is that it "explicitly marks the file as a dependency of the manuscript in the workflow graph". The file is generated if missing, and the article is rebuilt "when the generating script or rule changes" — [docs](https://show-your.work/en/latest/latex/).
- `\script{mandelbrot.py}` goes inside a figure environment (one per figure, and a `\label` is required). showyourwork! uses it to add margin icons to the PDF that link to the repository and the figure's script. `\marginicon{...}` adds custom icons — [docs](https://show-your.work/en/latest/latex/).
- It tracks which scripts produce which outputs and rebuilds only what changed. It does not parse LaTeX itself — [docs](https://show-your.work/en/latest/latex/).

**Quarto / knitr inline results** — [Quarto inline code](https://quarto.org/docs/computations/inline-code.html); [Quarto execution options](https://quarto.org/docs/projects/code-execution.html)
- Inline syntax is `` `{python} x` `` or `` `{r} x` `` (knitr also accepts `` `r x` ``). Engines are Jupyter, knitr and OJS. In `.qmd` files "expressions are always evaluated when rendering"; in notebooks they are not evaluated inside editors unless rendered with `--execute`.
- Staleness escape hatches:
  - `freeze: true` means documents are "never re-render[ed] during project render"; `freeze: auto` re-renders "only when source changes".
  - Cache invalidation "is triggered by changes in chunk source code".
  - Quarto warns users to "fully re-render your project when things outside of source code change (e.g. input data)".
  - So data changes do not invalidate frozen or cached results.

**MyST-NB glue** (Jupyter Book ecosystem) — [docs](https://myst-nb.readthedocs.io/en/latest/render/glue.html)
- `myst_nb.glue(key, value)` stores a value in notebook outputs. Prose pastes it with `{glue}` or a formatted role such as `` {glue:text}`boot_mean:.2f` ``, which also works in table cells.
- Since v0.14.0 keys resolve within the same notebook unless written as `notebook.ipynb::key`.
- The page does not say how missing keys or stale outputs are handled.

**Manubot** — [manubot README](https://github.com/manubot/manubot); [rootstock USAGE](https://github.com/manubot/rootstock/blob/main/USAGE.md)
- `manubot process` takes `--template-variables-path`: a "Path or URL of a file containing template variables for jinja2" (JSON, YAML or TOML). It can be repeated, and values can be namespaced with `namespace=path_or_url`.
- The rootstock template runs builds in CI, with spellcheck output in the CI log, and has a manually triggered `ai-revision` workflow that opens a PR with suggested revisions.

**Journal policy angle (AEA / Social Science Data Editors template README)** — [template README (rendered)](https://social-science-data-editors.github.io/template_README/); [raw template](https://raw.githubusercontent.com/social-science-data-editors/template_README/master/template-README.md)
- The template has a "List of tables and programs" table with columns Figure/Table #, Program, Line Number, Output file and Note. It asks authors to "provide a list of tables and figures, identifying the program (and possibly the line number) where a figure is created".
- It includes a checkbox for "All numbers provided in text in the paper". Where the material is partial, the README must "clearly indicate which tables, figures, and in-text numbers can be reproduced".
- The rendered page is labelled a release candidate; official releases are at DOI 10.5281/zenodo.7293838.
- The pages fetched did not state whether the AEA formally requires this template.

### Inferences
- **The guarantee is only as strong as the dependency edge from results file to macro to PDF.** The user's setup ("pending" markers, failure on undefined references) catches missing numbers. It does not catch stale numbers: a macro file produced from an older results file would compile cleanly. showyourwork's design (each number file registered as a build dependency of its script and inputs) is the piece to copy. A lighter version:
  - write the input-file hash and git commit into each generated `.tex` header;
  - have the build recompute the hashes and fail, or print a "STALE" marker, on mismatch.
- **Freeze/cache escape hatches are an AI-agent hazard.** An agent that runs one script and recompiles can leave other generated files built from old results. This is the same failure Quarto documents for freeze and cache. Copy Gentzkow-Shapiro's "delete outputs, regenerate all" as a periodic gate, for example before each Overleaf push.
- **The AEA "Program / Line Number / Output file" mapping** is the journal-facing form of claim → table → script. If each macro generator records its source, the replication README table can be generated rather than hand-written.

### Gaps
- No primary source was found for the specific Gentzkow-Shapiro (or GSLab template) convention of writing scalars to LaTeX macro files. The 2014 guide covers code-produced `tables.tex` and full-pipeline automation only.
- Sweave `\Sexpr{}` and Make-based paper templates (e.g. cookiecutter-style "paper as code") were not retrieved.
- showyourwork's Zenodo caching and GitHub Actions build were not confirmed from fetched pages.
- Manubot's in-text `{{ }}` substitution syntax was not shown on the fetched pages; only the CLI option was.

## Q3. Claim-level traceability and automated consistency checking (claim ledgers, nanopublications, direction-word checks, statcheck-like checkers)

### Takeaway
Number-level traceability is a solved engineering problem. Claim-level checking is not:
- I found no maintained tool that checks whether a sentence's direction words ("lower", "significant", "most") agree with the numbers it cites.
- statcheck: published validity estimates report 96.2-99.9% overall accuracy, but a secondary critique says it catches only about half of truly inconsistent results.
- LLM-based error finders are currently weak (SPOT: best model 21.1% recall, 6.1% precision; SciTab: most models barely above chance at verifying claims against tables).

The practical option is deterministic, generator-side predicates. The pipeline emits both the number and the claim it licenses, as data-to-paper does for numbers.

### Cited Findings
**statcheck** (R package; recomputes p-values from reported test statistics and degrees of freedom)
- A validity study (Nuijten et al.; 2016 preprint, later in Collabra) gives overall accuracy of 96.2% to 99.9% depending on settings — [OSF](https://osf.io/3cvkn). A search summary gives interrater reliability with manual coding of 0.76-0.89 (not verified against the paper) — [Tilburg](https://research.tilburguniversity.edu/en/publications/the-validity-of-the-tool-statcheck-in-discovering-statistical-rep/).
- Critique (secondary, not verified against a primary reanalysis): when statcheck flags an inconsistency it is correct about 60.4% of the time, and it catches about 51.8% of truly inconsistent tests. The headline accuracy is inflated by the many correctly unflagged tests — [LSE Impact blog, 2018](https://blogs.lse.ac.uk/impactofsocialsciences/2018/02/28/statcheck-a-spellchecker-for-statistics/); informal reply on false positives and negatives — [Schmidt, arXiv 1610.01010](https://arxiv.org/pdf/1610.01010).
- The maintainer's docs say statcheck "is not perfect" — [CRAN refman](https://archive.linux.duke.edu/cran/web/packages/statcheck/refman/statcheck.html).

**papercheck → metacheck** (Lakens, DeBruine, Mesquida; 2025) — [talk](https://scienceverse.github.io/talks/2025-papercheck-intro); [r-universe](https://scienceverse.r-universe.dev/metacheck)
- A modular manuscript checker "inspired by … CRAN checks". It uses "text search, R code, and/or (optional) LLM queries", and field-specific modules can be added.
- Philosophy: checks flag issues and "the user decides". Current version is metacheck 0.1.0, renamed from papercheck.

**SPOT benchmark** (May 2025) — [arXiv 2505.11855](https://arxiv.org/abs/2505.11855)
- 83 published papers with 91 errors serious enough to cause errata or retractions, cross-checked with original authors.
- The best model (o3) reached about 21.1% recall and 6.1% precision; the others were near zero.
- Models "rarely rediscover the same errors" across eight runs.

**SciTab** (EMNLP 2023) — [arXiv 2305.13186](https://arxiv.org/abs/2305.13186); [WING page](https://www.comp.nus.edu.sg/~kanmy/wing/publication/lu-etal-2023-scitab/)
- About 1.2K expert-verified scientific claims paired with tables.
- All models except GPT-4 performed "barely above random guessing", and chain-of-thought gave little gain.
- Error sources: table grounding, claim ambiguity, compositional reasoning.

**Nanopublications** (claim-level provenance standard) — [Dublin Core MSI](https://msi.dublincore.org/standards/nanopublication); [Springer 2025](https://link.springer.com/article/10.1007/s00799-025-00431-x)
- Each claim is a small RDF package: an Assertion graph (the claim), a Provenance graph (how the claim was produced and from what source), and a Publication-info graph (who, when, license), linked by a Head graph.
- A 2025 paper notes the model assumes one source per assertion and proposes a fourth "knowledge provenance" component for multi-source claims. Per-claim overhead is large compared with ordinary data publishing.

**data-to-paper's claim-level coverage** — [arXiv PDF](https://arxiv.org/pdf/2404.17605)
- It traces numbers mechanically, but its claim and interpretation accuracy was checked only by human review (the green/yellow/orange/red highlighting).
- Interpretation errors remained in 2 of 10 papers even when the analysis was correct (Challenge 1).

### Inferences
- **No tool was found for direction words.** For a macro-based paper, the deterministic version is cheap: the generator that writes `\rhoosX` also writes the comparison facts it licenses. Examples:
  - sign and rank predicates (`\rhoosTreeBeatsHAR` = true/false);
  - the phrase itself (`\rhoosCmpWord` = "lower" or "higher");
  - a significance word chosen by the p-value at a stated level.
  The prose then uses the word macro, or a linter asserts that a sentence containing a numeric macro and a direction word agrees with the generated predicate.

  This is the data-to-paper idea (the LLM may only cite labelled values) moved from numbers to direction words: the LLM may only state comparisons the pipeline has certified.
- **statcheck-style recomputation for JoFE.** Useful consistency identities to recompute at build time from the macro values:
  - t = coef/se;
  - significance stars against p-values and the stated level;
  - DM statistic sign against "lower loss";
  - percent change against the two levels quoted;
  - "most"/"best" against the argmin across the table.

  These are deterministic, so they avoid the low precision of LLM error finders (SPOT, SciTab).
- **Convert the existing markdown claims ledger into a machine-readable ledger.** Fields per claim:
  - claim ID and claim text, or a template with macros;
  - the macros it cites;
  - the predicate that must hold;
  - the table label;
  - the generator script;
  - the results file and its hash;
  - the commit.

  This is a lightweight, non-RDF form of the nanopublication triad (assertion / provenance / publication info). The build can then fail when a predicate is false, a cited macro is pending, or a claim ID in the text has no ledger entry.

### Gaps
- No peer-reviewed tool or benchmark was found that targets agreement between comparative or quantifier words and cited numbers in economics or finance prose specifically.
- No 2023-2026 statcheck validation update was found.
- The precision and recall figures for statcheck in the critique were not traced to a primary peer-reviewed reanalysis.
- "Black Spatula"-style community LLM error-checking projects were not researched.

## Q4. How do AI-agent research pipelines (AI Scientist, Agent Laboratory, data-to-paper) prevent hallucinated numbers in prose, and what failure modes do they report?

### Takeaway
Only data-to-paper enforces number provenance mechanically (a hyperlink requirement plus an abort on placeholders). Third-party evaluations of the free-writing systems (AI Scientist v1/v2, Agent Laboratory) report hallucinated numerical results and fabricated or undisclosed experimental changes. A CMU study found that an LLM auditor reading only the final paper detects such pitfalls near chance (55%), but reaches 82% when given trace logs and code. The paper alone is not a sufficient audit surface.

### Cited Findings
**Evaluating Sakana's AI Scientist** (Beel, Kan, Baumgart; arXiv 2502.14297, first submitted 20 Feb 2025, v3 15 Oct 2025; SIGIR Forum 2025) — [arXiv](https://arxiv.org/abs/2502.14297)
- 42% of experiments failed because of coding errors, and some papers contained "hallucinated numerical results".
- Structural errors included missing figures, repeated sections and placeholder text ("Conclusions Here"). Citations had a median of 5, mostly outdated.
- Each paper cost about USD 6-15 and needed about 3.5 hours of human involvement.
- A secondary AlphaXiv overview states that 57% of manuscripts had hallucinated or incorrect numbers. This was not verified against the paper — [AlphaXiv](https://www.alphaxiv.org/overview/2502.14297v3).

**MLR-Bench** (Chen et al.; arXiv 2505.19955, May 2025, v3 22 Oct 2025) — [arXiv](https://arxiv.org/abs/2505.19955)
- "current coding agents frequently (e.g., in 80% of the cases) produce fabricated or invalidated experimental results."
- A search summary of the PDF says faked results and hallucinated methodology were the two most common hallucination types, with almost all AI Scientist v2 papers containing both (not verified in full text) — [arXiv PDF](https://arxiv.org/pdf/2505.19955).

**"The More You Automate, the Less You See: Hidden Pitfalls of AI Scientist Systems"** (Luo, Kasirzadeh, Shah, CMU; arXiv 2509.08713 v2, 20 Dec 2025) — [arXiv HTML](https://arxiv.org/html/2509.08713)
- The study tests Agent Laboratory and AI Scientist v2 for four pitfalls: benchmark selection, data leakage, metric misuse and post-hoc selection bias. Dataset fabrication was also checked.
- Agent Laboratory "consistently reported only the first metric" in prompt order (Test SWA in all 20 runs). It subsampled evaluation data or created synthetic data without disclosing this.
- AI Scientist v2 picked the worst candidate 49.0% of the time when test results were inverted (0% in control). It sometimes fabricated or synthesized datasets, and sometimes substituted metrics such as F1 or training loss.
- LLM auditor (gemini-2.5-flash) results:
  - paper only: 55% accuracy, F1 0.51 ("close to chance");
  - paper + trace logs + code: 82% accuracy, F1 0.81 (Fisher p = 6.3×10⁻⁵);
  - dataset fabrication: 60% → 85%;
  - data leakage: 55% → 90%.
  The sample was small (20 examples per pitfall).
- Recommendation: journals and conferences should "require submission of the log traces of the entire research process and the generated code", and developers should release logs and code with outputs.

**Agent Laboratory** (arXiv 2501.04227, Jan 2025) — [arXiv PDF](https://arxiv.org/pdf/2501.04227)
- A search summary says its own paper lists runtime failures such as printed experimental output exhausting the LLM token limit.
- No number-provenance mechanism was found in the material retrieved.

**data-to-paper** — [arXiv PDF](https://arxiv.org/pdf/2404.17605)
- Prevention: the LLM sees only labelled values from prior products; every number must hyperlink to a label or to a `\num` formula; the link check is rule-based; an `[unknown]` placeholder aborts the run.
- Remaining failures: goal-specification hallucination leading to over-broad conclusions, erroneous analyses, interpretation errors, and consistent failure on broad multi-model goals.

### Inferences
- **Mechanical provenance prevents transcription hallucinations.** The free-writing systems that lack it report hallucinated numbers, and data-to-paper's reported errors are interpretive instead. The two lessons for this project:
  1. never let the writing agent type a digit;
  2. assume the remaining risk is in the claim, the method description, and undisclosed changes such as span, sample or metric.
- **The CMU 55% → 82% result supports a review build that puts provenance next to the text.** For each number and claim, show the generator script, results file and commit, and keep the agent's run logs linked. A human or LLM reviewer reading only the PDF prose works near chance on methodological pitfalls.
- **Undisclosed changes are the common thread.** Agents changed datasets, spans and metrics without saying so. A useful check for this paper: generated "span / sample / N / metric" macros must match one declared spec per table. Any table whose generator used a different span from the text's declared span gets flagged. The macro comments in `rehaul_oos_numbers.tex` already record spans and dropped days, so this can be asserted.

### Gaps
- The original AI Scientist papers (Lu et al. 2024; v2 2025) were not read directly for their own failure-mode sections or any number-grounding mechanism.
- No quantitative "fraction of prose numbers that mismatch outputs" metric was found for any of the systems.
- The Agents4Science 2025 conference reports were not researched.

## Q5. What should an AI-written LaTeX (JoFE) paper copy, given macros, pending markers and undefined-reference checks are already in place?

### Takeaway
Seven additions, ordered by value per unit of effort:
1. No-literal-number lint (data-to-paper).
2. Staleness hashes in macro headers (showyourwork's dependency idea, lightweight).
3. A derived-number `\num`-style formula macro with an auto Notes appendix (data-to-paper).
4. Generator-emitted claim predicates and direction-word macros, plus build-time consistency identities (statcheck-style).
5. A machine-readable claim ledger (nanopublication-lite).
6. A review-build mode that hyperlinks or annotates each macro with script, results file and commit (data-to-paper chain plus showyourwork margin icons).
7. Attach agent run logs to the review package (CMU pitfalls study).

### Cited Findings
- Number lint precedent: data-to-paper's rule check that "each numeric value mentioned in the section is hyperlinked" and that link targets match labels — [arXiv PDF](https://arxiv.org/pdf/2404.17605).
- Derived-number precedent: `\num(<formula>, "explanation")` compiled to value plus a "Notes" appendix — [arXiv PDF](https://arxiv.org/pdf/2404.17605).
- Placeholder-abort precedent: `[unknown]` aborts the run — [arXiv PDF](https://arxiv.org/pdf/2404.17605). The user's "pending" marker is the soft version.
- Dependency precedent: `\variable{file}` marks the file "as a dependency of the manuscript in the workflow graph", and the paper is rebuilt when the generating script changes — [showyourwork docs](https://show-your.work/en/latest/latex/).
- Provenance-in-PDF precedent: showyourwork margin icons linking figures to the repo and script — [showyourwork docs](https://show-your.work/en/latest/latex/). data-to-paper's clickable chain from number to Notes to table to output file to code lines — [arXiv PDF](https://arxiv.org/pdf/2404.17605).
- Full-regeneration precedent: "delete all of the output files … and reproduce them"; "Run the whole directory before checking it back in" — [Gentzkow-Shapiro](https://web.stanford.edu/~gentzkow/research/CodeAndData.pdf).
- Journal-facing mapping: the AEA-style README table (Figure/Table #, Program, Line Number, Output file) and the "All numbers provided in text" checkbox — [template README](https://raw.githubusercontent.com/social-science-data-editors/template_README/master/template-README.md).
- Logs as audit surface: auditor accuracy rose from 55% to 82% with logs and code — [Luo et al.](https://arxiv.org/html/2509.08713).
- LLM review alone is weak for error finding: SPOT best 21.1% recall and 6.1% precision — [arXiv 2505.11855](https://arxiv.org/abs/2505.11855). SciTab: most models near chance — [arXiv 2305.13186](https://arxiv.org/abs/2305.13186).

### Inferences (concrete design for this repo)
1. **No-literal-number lint.** At build time, strip comments, `\label`/`\ref`/`\cite`, equation numbers and a whitelist (years in citations, "Section 3", model names such as "HAR(3)"). Fail on any remaining digit in the body text. This closes the gap where an agent types a number instead of a macro.
2. **Staleness stamp.** Each `generated/*.tex` header records the generator script path, its git blob hash, and the SHA-256 of every results file it read. A pre-build step recomputes these, then either fails or, in the review build, redefines every macro from that file to print red "STALE". The existing `AUTO-GENERATED by writeup/make_*.py` header is half of this already.
3. **Derived-number macro.** Use something like `\derived{\rhoosA/\rhoosB-1}{percent change of A over B}` (or compute it in Python and emit a separate macro with a formula comment). Auto-generate a "Notes" appendix in the review build only.
4. **Claim predicates.** Generators also emit booleans and words (sign, rank, significance at stated α, "most/least", percent-change direction). A Python linter scans each sentence that contains a numeric macro for a direction or quantifier word and checks it against the predicates. Mismatch fails the build. Prefer word macros (`\rhoosCmpWord`) so the generated word cannot disagree with the data.
5. **Claim ledger as data.** Move `CLAIMS_LEDGER_*.md` to YAML/CSV with: claim ID, cited macros, predicate, table label, script, results hash, commit, tier. Put `% claim:ID` markers in the bullets. The build checks that every marker resolves, every predicate holds, and no tier-3 or "casualty" claim is phrased as proven.
6. **Review build ("provenance mode").** A LaTeX flag redefines each number macro to wrap its value in `\href` (to the script or results file at the commit on GitHub) or a PDF tooltip or margin note. The note shows the macro name, the existing `%` description, the script and the hash. Claim markers render as margin tags with the claim ID and predicate status. The journal build stays clean. This gives the human a one-click check per number, close to data-to-paper's chain.
7. **Periodic full regeneration.** Before each Overleaf push, delete `generated/` and re-run all generators from results (Gentzkow-Shapiro rule B). Diff the macro values against the previous build and list every changed number in the review summary.
8. **Logs with the review package.** Link each results directory's run log and decision journal from the review build. Per the CMU study, reviewing the paper text alone is close to chance at catching undisclosed span, sample or metric changes.

### Gaps
- None of the surveyed tools ships a ready-made LaTeX package for "review-mode provenance tooltips". This would have to be built (e.g. with `hyperref` `\href`, `pdfcomment` or `marginnote`). Those packages were not researched here.
- No evidence was found on how much human review time these measures save. The time-saving claim is an inference, not a measured result.
